### Group 13: Periods and the operating calendar

| Variable | Documented default | Degradation notice |
|---|---|---|
| OPERATING_WINDOW_SOURCE | Derived from PLANNING_PERIOD_LENGTH_DAYS by the derivation rule below. | The published dates of your operating window are not read from any source, so the window used here was derived. The dates used are printed; if they are wrong, every due-date weighting in this report shifts with them. |
| OPERATING_WINDOW_DERIVATION_RULE | **THE PERIOD NAME DECIDES WHICH OF TWO RULES APPLIES, AND THE NAME IS THE AUTHORITY.** Where PLANNING_PERIOD_NAME denotes a CALENDAR UNIT, a month, a quarter, a half or a year, the window is that calendar unit ENTIRELY: it opens on its first day and closes on its last, whatever PLANNING_PERIOD_LENGTH_DAYS says, and the nominal length is then used only for horizon arithmetic such as the near horizon. Where the period name denotes a ROLLING or a FISCAL window that is not a calendar unit, a four-week cycle or a thirteen-period year, the window opens the day after the previous window closes and runs PLANNING_PERIOD_LENGTH_DAYS. **THE COVERING INVARIANT, WHICH BOTH FORMS MUST SATISFY: no day inside the period a window is NAMED for may fall outside that window.** The rule that failed it: a nominal length of thirty days anchored on the first of a calendar month left the thirty-first of a thirty-one day month outside the window named for that month, so a commitment falling on the last day of the month being planned banded as belonging to the NEXT window and was weighted down. A person told this is their plan for a named month is entitled to have every day of that month in it. Where a derivation cannot satisfy the invariant, it is a binding error and the run says so; it is never resolved by shortening the month. | The window was derived by the standing rule rather than read from a published calendar, and the exact dates are printed above the list. Because your period is named for a calendar unit, the window is that whole unit: it opens on its first day and closes on its last, so no day of it falls outside its own window. The nominal length you bound is used for horizon arithmetic and not to cut the window short. |
| PLAN_AHEAD_RULE | If today falls in the last third of the current window, plan the next one. | The standing plan-ahead rule was used. The period this plan covers is named at the top of the report. |
| REPORTING_CALENDAR_IS_NOT_AUTHORITY | true. | Fiscal and calendar quarter ends are treated as inputs the operating window converts, never as due dates, which is the only permitted setting. |
| PERIOD_TOKEN_MAP | The generic tokens: Q1 to Q4, H1, H2, and the month names, each resolved through the operating window. | No local period vocabulary is bound. A period token in a work item name that is not on the generic list cannot be dated, and every such item is named in the audit and dropped from scoring rather than guessed at. |
| CLOSE_HORIZON_DAYS | 90 days, counted forward from the LAST DAY OF THE PLANNED WINDOW and never from the run date. | The near horizon was not set, so ninety days from the close of the window being planned was used. The anchor date itself is printed in the audit, because anchoring on the run date instead would move items between the two lowest close weights and reorder the published list. |
| CLOSE_WEIGHTS | 1.00 confirmed inside the PLANNED window; 0.75 named for the planned window with an unreadable date; 0.50 inside the NEXT window; 0.35 after the next window but within CLOSE_HORIZON_DAYS of the PLANNED window's close; 0.20 beyond that horizon, or expired in a window that closed before the planned one opened. EVERY band is anchored on the window BEING PLANNED, never on the run date, so a plan built weeks early bands identically to the same plan built on the window's first morning. The five triggers are exhaustive: no derivable date falls between two of them. **THE MAP FROM THE NINE CLOSE STATES ONTO THESE FIVE WEIGHTS, WRITTEN OUT BECAUSE IT WAS ONLY INFERABLE BEFORE AND A MAP THAT MUST BE INFERRED IS A MAP TWO IMPLEMENTERS WILL DRAW DIFFERENTLY:** `due_this_plan` takes 1.00; `date_unreadable` takes 0.75; `due_next_window` takes 0.50; `due_on_near_horizon` takes 0.35; `due_beyond_horizon`, `due_before_plan_starts`, `passed_this_window` and `passed_earlier_window` all take 0.20, which is what the file means when it says four states sit at the floor weight and are four different facts; and `no_derivable_date` takes NO WEIGHT AT ALL, because it is dropped from scoring and named rather than banded. Nine states, five weights and one exclusion, with every state on exactly one of them. | The standing close weights were used, and every item that took a fallback weight is named with the weight it took. The 0.35 band exists because a date after the next window but still inside the near horizon previously fell in no band at all, and a date in no band is either dropped or banded down arbitrarily. |
| UNDATED_ITEM_TREATMENT | dropped_from_scoring. | An item with no derivable date contributes nothing, which is the only permitted setting. Every such item is named. |
| CARRYOVER_LABEL | The phrase "prior period carryover". | The standing carryover label was used on expired work kept visible at the floor weight. |
| CYCLE_POSITIONS | SET, TRACK, MIDPOINT, CLOSE. | The standing run modes were used. |
| CYCLE_POSITION_NAMES | The same four words. | Your organization's names for the review points are not bound, so the generic names are used in headings. |
| GOAL_REVIEW_CADENCE | quarterly. | The review cadence has not been recorded, so quarterly was assumed and is stated wherever cadence affects a date. |
| REFERENCE_VALIDITY_PERIODS | Every cached block expires at the end of the current calendar year. | No per-reference validity dates have been set, so every cached reference expires at year end. A block past that date is refetched, or used and marked stale. |
