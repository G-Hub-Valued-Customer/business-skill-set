# GROUP 5: POPULATION SHAPE

The bundle must serve both a FIXED enumerable population (branches, accounts,
facilities, machines, routes) and a FLOWING pipeline (claims, deals, tickets,
cases, work orders), and many businesses have one of each. A business may declare
more than one population. The shape is a property of a declared population, not
of the company, and it is detected per population during binding. It changes what
"the population" means downstream. It does not change the deliverable shape. See
SD-POP-23.

TAXONOMY SHAPE, POPULATION_SHAPE. A KEYED SET of declared populations, not one
object. A business may declare one; a business that has a roster of containers
AND a stream moving across them declares two, and each run names which it scored.
Shape is a property of a declared population, not of the company. See SD-POP-23.

Each entry carries:
- `key`: stable id for this population, never renamed. Every run names it in the
  front panel, and every skill resolves which population it is scoring against
  this key.
- `mode`: FIXED or FLOW, FOR THIS POPULATION ONLY.
- `unit_singular` and `unit_plural`: the noun, for this population.
- `unit_level_key`: the SCOPE_LEVELS key at which one unit of THIS population
  sits. Where two populations sit at different levels, each carries its own.
- `enumeration_source`: where the full roster comes from. FIXED only.
- `census_basis`: the date the roster is taken as of. FIXED only.
- `entry_field` and `exit_field`: the concept keys holding the date a unit
  entered and left. FLOW only.
- `stage_field`: the concept key holding the current stage. FLOW only.
- `stages`: the ordered stage list. FLOW only.
- `aging_basis`: which date staleness is measured from. FLOW only.
- `reopen_allowed`: whether a unit can re-enter after exit. FLOW only, and it
  cannot be inferred from columns alone.

Every mode-conditional field above is CONDITIONAL on THAT POPULATION's mode, not
on a single company-wide mode, and each carries a default and a notice in
SECTION A2.

**WHERE MODE IS UNBOUND IT IS INFERRED, BY ONE PROCEDURE.** An unbound mode does
not stop a run; it produces a provisional run. The inference procedure is the
three tests in SD-POP-24 and nowhere else: the roster test, the entry-and-exit
test, and the replacement test which decides. There is exactly ONE procedure in
this bundle, and any other statement of one is a defect. The inferred mode is
recorded at MEDIUM confidence, printed in the front panel with the evidence that
produced it, and never written to the config by a run.
